# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Marv (the `marv` command) is a terminal coding agent (like Claude Code) written in TypeScript on **Bun** with an **Ink** (React-for-terminal) TUI. It is being built milestone by milestone; the roadmap lives in `~/.claude/plans/im-planning-on-making-staged-eclipse.md`. The owner is learning how agents work, so explain the *why* of each change.

## Commands

```sh
bun install
bun run dev                 # run the TUI from source (same as `marv`)
bun test                    # all tests
bun test tests/commands     # one file (path substring filter)
bun test -t "streams"       # tests whose name matches
bun run typecheck           # tsc --noEmit
bun link                    # (once) puts `marv` on PATH, pointing at src/cli.tsx — no build step
```

## Architecture

- `src/cli.tsx` is the `bin` entry (Bun shebang). It handles `--version`/`--help`, takes the project root from the current directory, reads the project's `AGENTS.md` once (`loadInstructions` in `src/prompt.ts`, capped at 20k chars), then renders `<App>`.
- **Config (`src/config/config.ts`)**: two layers, later wins: `~/.marv/config.json` (zod-validated, written with mode 0600 because it can hold the API key), then env vars (`OPENROUTER_API_KEY`, `MARV_MODEL`, `OLLAMA_HOST`). `PRESETS` describes each provider (label, base URL, which env var holds its key, default model). `FileConfig` is what's on disk; `resolveConfig()` produces the `Config` the app runs on. `MARV_CONFIG_DIR` relocates the config, so use it when testing by hand to keep your real config untouched.
- **Setup (`src/ui/Setup.tsx`)** runs on first run, or when OpenRouter has no key, and again via `/setup` (and `/model`, starting at the model step). It renders *in place of the prompt* (pinned at the bottom, below the transcript), not as a separate screen.
- `createProvider(config)` in `src/provider/index.ts` is the only place that maps config to a concrete `Provider`. OpenRouter uses `OpenAICompatProvider` (`src/provider/openai-compat.ts`: plain `fetch` to `POST {baseUrl}/chat/completions`, SSE parsed by `src/provider/sse.ts`; tool calls arrive in fragments keyed by `index` and are assembled before being emitted; `stream_options.include_usage` gets token counts incl. cached tokens). Ollama uses `OllamaProvider` (`src/provider/ollama.ts`: native `POST /api/chat`, NDJSON), because only the native API can set the context window (`num_ctx` = config `contextLength`, default 32768; Ollama's own default of 4096 is too small for an agent). `think` follows `/think` (off by default: local thinking models can otherwise reason for minutes).
- `src/app.tsx` holds all session state. The phases are `splash` → `main`, plus an optional setup overlay. It keeps two separate histories:
  - `items`: the **transcript the user sees**, including the welcome banner, help text, and errors.
  - `conversation` (a ref of `ChatTurn[]`): **what the model sees**: user and assistant turns, the assistant's tool calls, and tool results.
  Keep them separate; Marv's own notices must never leak into the model's context.
- **Agent loop (`src/agent.ts`)**: `runAgent()` sends the conversation plus tool definitions, runs any tools the model asks for (via an injected `runTool`), appends the results, and repeats until a plain answer, an error, ctrl+c, or 25 steps. It yields `LoopEvent`s and knows nothing about the UI or vendors; `App.send()` turns the events into transcript entries (tool calls are `role: "tool"` messages updated in place: running → summary or error). Every tool call gets a result, even after ctrl+c, or the next request would be rejected.
- **Tools (`src/tools/`)**: each is a name, a description the model reads, a zod `input` schema (sent as JSON schema; also validates what comes back), a `label` for the transcript, and `run()` → `{ output, summary }`. Register new ones in `tools` in `src/tools/index.ts`. Read tools (`read_file`, `glob`, `grep`) run freely; tools with `kind: "write" | "execute"` (`edit_file`, `write_file`, `bash`) need approval: `runTool()` first calls the tool's `preview()` (a diff, or the command; a `ToolError` there means the call can't succeed, so the user is never asked to approve it), then `ctx.approve()`, which the App answers with the `Approval` prompt (yes / yes and don't ask again for the tool's `scope` this session / no). A "no" returns a `declined` result and `runAgent` stops so the user can redirect. `edit_file` replaces text that must match exactly once (or `replace_all`) and is re-planned at apply time in case the file changed while the user decided. `runTool()` never throws: bad JSON, invalid input, and `ToolError`s become error results the model can recover from. All paths go through `resolveInProject()` (`src/tools/files.ts`), which rejects anything outside the project root, including via symlinks. Files are listed with `git ls-files` (so `.gitignore` applies), falling back to a walk that skips `node_modules`, `.git`, `dist`, etc.
- **Skills (`src/skills.ts`, `src/tools/skill.ts`)**: `.marv/skills/<name>/SKILL.md` (project) and `~/.marv/skills/<name>/SKILL.md` (personal; a project skill wins a name clash), YAML frontmatter (`name`, `description`) parsed with `Bun.YAML`, then the instructions; extra files in the folder are listed. Loaded once in `cli.tsx`; broken ones are skipped and reported (startup notice and `/skills`). Progressive disclosure: only names and descriptions go into the system prompt (stable all session, so the cache holds); the model loads the full instructions with the `skill` tool (only offered when skills exist; `file` reads one of the skill's files, confined to its folder). `/<skill> args` sends the instructions with the request directly (the transcript shows what was typed); skills also appear in the `/` menu. Measured with local models: a task-shaped request ("write release notes…") made qwen3.5:9b load the matching skill 4/5 times and gemma4:12b 5/5; a greeting skill was ignored. Descriptions should name the task and when to use it.
- **Sandbox (`src/sandbox.ts`)**: `bash` runs inside bubblewrap: the system read-only, the home folder replaced by an empty one (toolchains like `~/.bun`, git config, and `~/.marv/skills` re-mounted read-only), the project the only writable place, no network unless the call sets `network: true`, a cleared environment (no API keys), its own PID namespace (killing it kills everything it started). Output is stdout+stderr combined, capped (start and end kept). `/sandbox off` runs commands directly (still approved, with a warning in the prompt); without bwrap the prompt warns too. Outside the sandbox commands start under `setsid` so a timeout or ctrl+c kills the whole process group.
- **Prompt cache (don't break it)**: providers reuse work for an identical prompt *prefix* (measured on Ollama: a follow-up turn's prompt in 76 ms instead of 1.2 s; one changed letter in the system prompt and it's back to 1.2 s). So: the system prompt is built once per session (`useMemo` in `App`), `toolSpecs` is a constant, `conversation` is only appended to (never edited or trimmed; `/clear` resets it), and adapters serialize deterministically. `tests/agent.test.ts` checks that every request extends the previous one exactly. The status bar shows the last request's size (`12.3k/32.8k ctx` when the window is known) and the cache hit rate when the provider reports it (OpenRouter); Marv warns once when Ollama's window is 85% full.
- **Provider seam (`src/provider/types.ts`)**: every provider implements `Provider.stream(history, { system, tools, signal }) → AsyncIterable<AgentEvent>` (`text_delta`, `thinking_delta`, `tool_call`, `usage`, `done`, `error`), converting its native stream into Marv's own events. The UI never sees a vendor format. Errors become `error` events with an actionable message (bad key → /setup, unknown model → /model, unreachable → is it running?). The system prompt lives in `src/prompt.ts`. Model lists for the picker come from `src/provider/models.ts` (OpenRouter `/models`, filtered to tool-capable; Ollama `/api/tags` + `/api/show`).
- **Rendering**: Marv runs full-screen in the terminal's alternate screen, so there is no terminal scrollback. Ink's options live in `src/render-options.ts`; keep `incrementalRendering: true`, because without it every update (each martian frame, each keystroke) erases and redraws the whole screen, which flickers in terminals like GNOME Console. `tests/render-options.test.tsx` guards this. The root `<Box>` is sized to the window; `ScrollView` (`src/ui/ScrollView.tsx`) takes the leftover height and scrolls the transcript itself (PgUp/PgDn or the mouse wheel, follows the bottom until you scroll up; `followKey` snaps back on submit). The prompt and status bar are pinned below it. Don't use `<Static>` here: in the alternate screen its output would scroll off and be lost. The whole transcript stays mounted, so **ink is patched** to skip drawing nodes entirely outside the visible (clipped) rows: unpatched, Ink wraps and draws every scrolled-away message on every frame, and a 60-entry session took ~270 ms per keystroke (now ~30 ms). `tests/render-performance.test.tsx` guards this. Wheel scrolling glides: notches add to a distance that a 20 ms timer covers a third at a time (at least a row), and Ink draws up to 60 frames/s (`maxFps: 60`); 20 ms keeps every step in its own frame (16 ms beat against Ink's limiter and stuttered). Two more patches keep frames cheap (~7 ms): **string-width is patched** (`patches/string-width@8.3.0.patch`) to cache widths and skip its per-character emoji regex for characters that can't be emoji (it was ~36% of CPU while scrolling; `tests/string-width.test.ts` pins its answers), and the Ink patch skips `findStaticNode`'s walk of the whole tree after every commit unless a `<Static>` was ever created.
- **Mouse (`src/mouse.ts`)**: Ink has no mouse support, so Marv turns on SGR mouse reporting (mode 1002: presses, drags, wheel), wraps `stdin.read()` to strip mouse codes before Ink parses them, and emits `MouseEvent`s on the `mouse` emitter. Mouse mode is terminal-wide, so it is turned off in a `process.on("exit")` handler.
- **Selection (`src/selection.ts`, `src/clipboard.ts`)**: with mouse reporting on, the terminal can't select text, so Marv does: drag highlights, release copies (wl-copy / xclip / xsel / pbcopy, falling back to OSC 52), a click or any key clears it. The selection is stored in *transcript* rows, not screen rows (the transcript's `ScrollView` publishes its position and scroll via `onViewport`), so the highlight stays on its text while scrolling, and dragging past the top or bottom auto-scrolls. Only visible rows are ever drawn, so the store remembers each transcript row's text as it passes through the viewport and copies from that (like a terminal's scrollback); a resize or `/clear` resets it. **ink is patched** (`patches/ink@8.0.0.patch`, applied by `bun install`; edit with `bun patch ink`, then `bun patch --commit node_modules/ink`) with a `transformOutput(frame) → frame` render option, through which the store sees each frame and draws the highlight, and a `repaint()` that re-applies it to the last frame. Moving the highlight therefore costs ~3 ms instead of a full ~30 ms React render + layout + draw.
- **Slash commands (`src/commands/index.ts`)** are pure functions that return a `CommandAction` (`print` | `clear` | `setup` | `model` | `thinking` | `sandbox` | `skill` | `exit`) and receive a read-only `CommandContext` (current config). The App applies the action. Add new commands to the `commands` array; they automatically show up in the `/` menu (`PromptInput`: ↑/↓ select, Enter runs the highlighted one, Tab or → completes so you can add arguments). A `print` action with `markdown: true` (e.g. `/skills`) is rendered through the Markdown renderer, so lists get hanging indents.
- **Replies are Markdown** (`src/ui/Markdown.tsx`): `marked.lexer()` turns the text into tokens and each becomes Ink boxes: list markers and quote bars sit in fixed-width columns (hanging indents), inline code is colored without backticks, code blocks get a left rule and their language, tables are aligned as plain text. While a reply streams (`streaming` prop), `createStreamLexer()` caches the blocks before the last safe boundary and re-parses only the unfinished end, because `marked` slows down faster than the text grows (~20 ms at 11 KB); finished messages are parsed whole once. An unclosed code fence renders fine mid-stream. The system prompt tells the model its replies are rendered as Markdown.
- **Render budget**: `App.send()` batches streamed tokens and reaches React at most every 33 ms (`STREAM_FLUSH_MS`, matching Ink's 30 fps cap), flushing immediately at step ends; `MessageView` and `Transcript` are memoized so a transcript change only re-renders the entries that changed. `tests/render-performance.test.tsx` guards keystroke cost and stream batching.
- Colors live only in `src/ui/theme.ts`. Message markers (`●`, `>`) sit in a fixed 2-column `Gutter` box: a Text with a trailing space (`"● "`) is laid out 1 column narrower than it's drawn, so the text beside it overflows and loses a character per wrap (`tests/messageview.test.tsx`).

## Conventions

- Imports use explicit `.ts`/`.tsx` extensions (`allowImportingTsExtensions` + `verbatimModuleSyntax`; use `import type` for types).
- UI tests use `ink-testing-library`. Pass `splashMs={0}` to skip the splash, `makeProvider={() => new FakeProvider()}` (`tests/fake-provider.ts`) for an instant, offline stream (or a `ScriptedProvider` to script tool calls step by step), a `root` temp dir for the tools, and a `ConfigStore` on a temp dir.
- Providers: OpenRouter (default model `anthropic/claude-sonnet-5.5`) and Ollama (local, no key). A saved provider Marv no longer knows (e.g. the removed `echo`) is dropped on load, which reopens setup. Tests never hit the network: the adapters are tested against a local `Bun.serve`, and `App` takes `loadModels`/`makeProvider` props.
